27 下游弹性

既然我们已经讨论了如何通过冗余和分区在架构层面降低了故障的影响，接下来我们将深入探讨阻止故障从一个组件或服务传播到另一个组件或服务的战术弹性模式。在本章中，我们将讨论保护服务免受下游依赖故障影响的模式。

27.1 超时

在进行网络调用时，最佳实践是配置一个超时时间，以便在一定时间内未收到响应时使调用失败。如果调用时未设置超时，则有可能永远不会返回，正如第24章所述，不返回的网络调用会导致资源泄漏。因此，超时机制的作用在于检测连接性故障，并阻止其从一个组件向另一个组件连锁式传播。通常而言，对于那些可能永远无法返回的操作（例如获取互斥锁），超时是必不可少的。

不幸的是，一些网络API本身就没有设置超时的方法，而有些则默认没有配置超时。例如，JavaScript的XMLHttpRequest是用于从服务器异步检索数据的核心Web API，其默认超时时间为零1，即意味着永不超时：

var xhr = new XMLHttpRequest();
xhr.open("GET", "/api", true);
// 默认没有设置超时时间，因此需要显式设置它!
xhr.timeout = 10000; // 1万毫秒
xhr.onload = function () {
  // 请求完成
};
xhr.ontimeout = function (e) {
  // 请求超时
};
xhr.send(null);

fetch Web API是使用Promise实现的、用于替代XMLHttpRequest的现代方案。当fetch API最初被引入时，完全无法设置超时2。浏览器后来才通过Abort API添加了对超时的支持3。Python的情况也好不到哪里去；流行的requests库使用的默认超时时间是无穷大4。而Go的HTTP包默认不使用超时5。

Java和.NET的现代HTTP客户端做得更好，通常都带有默认超时。例如，.NET Core的HttpClient默认超时为100秒6。这虽然宽松，但可以说比完全没有超时要好。

根据经验法则，在进行网络调用时，我们应该始终设置超时时间，并且要警惕那些进行网络调用但不暴露超时设置的第三方类库。

但是，我们如何确定一个合适的超时时间呢？一种方法是基于期望的虚假超时率7来设定。例如，假设我们有一个服务调用另一个服务，并且我们愿意接受0.1%的下游请求（这些请求最终本应返回响应）会超时（即0.1%的虚假超时率）。为了实现这一目标，我们可以基于下游服务响应时间的第99.9百分位数来配置超时。

我们还需要建立良好的监控来测量网络调用的整个生命周期，例如调用的持续时间、接收到的状态码以及是否触发了超时。我们将在本书后面讨论更多关于监控方面的内容，但我想在这里强调的是，我们必须测量系统集成点发生的情况，否则我们将很难调试生产环境中的问题。

理想情况下，网络调用应该被封装在一个库函数中，该函数设置超时并监控请求，这样我们就不必为每次调用都需要记住做这些。或者，我们也可以使用位于同一台机器上的反向代理，它拦截我们的服务进程发出的远程调用。代理可以强制设置超时并监控网络调用，从而将这一职责从我们服务进程中剥离。我们在第18.3节讨论边车模式和服务网格时谈到过这一点。

27.2 重试

现在我们知道，客户端在进行网络请求时应配置超时时间。但当请求失败或超时时，客户端应该怎么做？此时客户端有两个选择：快速失败或重试请求。如果是短暂的连接问题导致了失败或超时，那么在经过一段退避时间后重试，成功的概率很高。然而，如果下游服务不堪重负，立即重试只会让情况变得更糟。这就是为什么我们需要逐步增大延迟时间以放缓重试，直至达到最大重试次数或距离初始请求已过去足够长的时间。

27.2.1 指数退避

为了设置重试之间的延迟，我们可以使用有上限的指数函数，其中延迟是通过将初始退避持续时间乘以一个在每次尝试后呈指数增长的常数来计算的，直到达到某个最大值（即上限）：

delay=min(cap,initial-backoff⋅2attempt)\text{delay} = min(\text{cap}, \text{initial-backoff} \cdot 2^{\text{attempt}})

例如，如果上限设置为8秒，初始退避持续时间为2秒，那么第一次重试延迟为2秒，第二次为4秒，第三次为8秒，任意下一次的延迟都将被限制在8秒以内。

尽管指数退避确实减少了对下游依赖的压力，但它仍然存在一个问题。当下游服务临时降级时，多个客户端很可能在同一时间遭遇请求失败。这将导致客户端同时重试，给下游服务带来负载峰值，这会使其性能进一步下降，如图27.1所示。

图 27.1: 重试风暴

为了避免这种群体行为，我们可以在延迟计算中引入随机抖动8。这会将重试请求分散到不同时间点，并平滑下游服务的负载：

delay=random(0,min(cap,initial-backoff⋅2attempt))\text{delay} = random(0, min(\text{cap}, \text{initial-backoff} \cdot 2^{\text{attempt}}))

主动等待并重试失败的网络请求并不是实现重试的唯一方法。在没有严格实时要求的批处理应用程序中，进程可以将失败的请求放入重试队列。同一个进程，或者也可能是另一个进程，可以在稍后从同一个队列中读取并重试失败的请求。

仅仅因为一个网络调用可以重试，并不意味着它就应该被重试。如果错误不是短暂的，例如，因为进程无权访问远程端点，那么重试请求就没有意义，因为它会再次失败。在这种情况下，进程应该快速失败并立即取消调用。正如第5.7章所讨论的，我们还应该理解重试一个非幂等且其副作用可能影响应用程序正确性的网络调用的后果。

27.2.2 重试放大

假设处理一个用户请求需要经过三个服务的链式调用。用户的客户端调用服务A，服务A调用服务B，服务B再调用服务C。如果从服务B到服务C的中间请求失败，B是否应该重试该请求？如果B确实重试了，A将感知到其请求的执行时间变长，使得更有可能触发A的超时。如果发生这种情况，A会重试请求，使得客户端更有可能触发其超时并进行重试。

在依赖链的多个层级进行重试会放大重试的总次数——服务在链中的位置越深，由于重试放大效应，它将承受的负载就越高（见图27.2）。

图 27.2: 重试放大效应实例

如果负载压力足够大，这种行为很容易使下游服务过载。这就是为什么，当我们有长依赖链时，我们应该考虑只在链的单个层级进行重试，而在所有其他层级快速失败。

27.3 断路器

假设一个服务使用超时机制来检测下游依赖是否不可用，并通过重试来缓解瞬时故障。如果故障并非瞬时的，且下游依赖持续无响应，那么它应该怎么做？如果服务持续重试失败的请求，必然导致其对客户端的响应变慢。反过来，这种缓慢可能会蔓延到系统的其余部分。

为了处理非瞬时故障，我们需要一种机制来检测下游依赖的长期性能下降，并从一开始就阻止新的请求被发送到下游。毕竟，最快的网络调用就是没有网络调用。这里所说的机制就是断路器，其灵感来源于电路中相同的功能实现。

断路器的目标是允许一个子系统失败，而不减慢调用者的速度。为了保护系统，对故障子系统的调用会被暂时阻止。之后，当子系统恢复且故障停止时，断路器会再次允许调用通过。

与重试不同，断路器完全阻止网络调用，这使得该模式对于非瞬时故障特别有用。换句话说，当预期下一次调用会成功时，重试是有用的；而当预期下一次调用会失败时，断路器是有用的。

断路器可以实现为一个具有三种状态的状态机：开启、关闭和半开启（参见图 27.3）。

图 27.3: 断路器状态机

在关闭状态下，断路器仅作为网络调用的直通通道。在此状态下，断路器会跟踪故障数量，例如错误和超时。如果在预定义的时间间隔内，故障数量超过某个阈值，断路器就会被触发并打开断路器。

当断路器处于开启状态时，不会尝试网络调用，并且会立即失败。由于处于开启状态的断路器可能对业务产生影响，我们需要考虑当下游依赖宕机时应该发生什么。如果该依赖是非关键性的，我们希望我们的服务能够优雅地降级，而不是完全停止。想象一架飞机在飞行中失去了一个非关键子系统；它不应该坠毁，而是应该优雅地降级到一个飞机仍然可以飞行和降落的状态。另一个例子是亚马逊的主页；如果推荐服务不可用，页面会在没有推荐内容的情况下渲染。这比完全无法渲染整个页面要好。

经过一段时间后，断路器会给下游依赖另一次机会，并转换到半开启状态。在半开启状态下，允许下一次调用通过到下游服务。如果调用成功，断路器将转换到关闭状态；如果调用失败，则转换回开启状态。

你可能会认为这就是理解断路器工作原理的全部，但细节决定成败。例如，需要多少次故障才能认为下游依赖宕机？断路器应该等待多长时间才能从开启状态转换到半开启状态？这确实取决于具体的上下文；只有通过使用过去的故障数据，我们才能做出明智的决定。
