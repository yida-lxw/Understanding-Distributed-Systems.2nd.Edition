11 协调规避

审视状态机复制的另一种方式是将其视为一个需要两个主要组成部分的系统：

  • 一个广播协议，它保证即使在出现故障的情况下，每个副本也能以相同的顺序接收相同的更新（也称为容错全序广播），
  • 以及一个在每个副本上处理更新的确定性函数。

不出所料，实现一个容错的全序广播协议正是状态机复制难以解决的原因，因为它需要共识1。更重要的是，对全序的需求造成了可扩展性瓶颈，因为更新需要由单个进程（例如，Raft中的领导者）顺序处理。此外，在网络分区期间，全序广播也不可用，因为CAP定理2同样适用于它3。

在本章中，我们将探讨一种无需完全排序但仍能提供有用保证的复制形式。但首先，我们需要讨论一下广播协议。

11.1 广播协议

在诸如互联网这样的广域网上进行网络通信，通常只提供点对点（单播）通信协议，例如TCP。但是，要向一组进程传递消息，则需要广播协议（组播）。这意味着我们必须在单播协议之上构建组播协议。这里的挑战在于，组播需要支持多个可能随时崩溃的发送方和接收方。

广播协议的特性由其提供的保证来定义。最大努力广播保证，如果发送方没有崩溃，消息将被传递给组内所有无故障的进程。实现它的一个简单方法是，通过可靠的链路将消息逐一发送给组内的所有进程（参见图 11.1）。然而，例如，如果发送方中途失败，某些进程将永远不会收到消息。

图 11.1: 最大努力广播

与最大努力广播不同，可靠广播保证消息最终会被传递给组内所有无故障的进程，即使发送方在消息完全传递之前崩溃。实现可靠广播的一种方法是，让每个进程在首次收到消息时，将其重新传输给组内的其他进程（参见图 11.2）。这种方法也被称为急切可靠广播。虽然它保证了所有无故障的进程最终都会收到消息，但代价高昂，因为它需要为一个包含 NN 个进程的组发送 N2N^2 次消息。

图 11.2: 急切可靠广播

可以通过仅将消息重新传输给进程的随机子集（例如，如图 11.3 中的2个）来减少消息数量。这种实现被称为Gossip广播协议4，因为它类似于谣言传播的方式。由于它是一种概率性协议，不能保证消息会被传递给所有进程。尽管如此，通过调整协议参数，可以使这种概率变得微乎其微。当需要向大量进程进行广播，而确定性协议无法扩展时，Gossip协议特别有用。

图 11.3: Gossip广播

尽管可靠广播协议保证消息会被传递给组内所有无故障的进程，但它们对消息的顺序没有任何保证。例如，两个进程可能以不同的顺序接收相同的消息。全序广播是一种可靠广播抽象，它建立在可靠广播提供的保证之上，并额外确保所有进程以相同的顺序接收消息。如前所述，一个容错的实现需要共识机制。

11.2 无冲突复制数据类型

现在，有一个想法：如果我们使用不保证全序的广播协议来实现复制，我们就不需要通过单一领导者来序列化写入，而是允许任何副本接受写入。但由于副本可能以不同的顺序接收消息，它们不可避免地会产生分歧。因此，为了使复制有用，这种分歧只能是暂时的，副本最终必须收敛到相同的状态。这就是最终一致性的本质。

更正式地说，最终一致性要求：

  • 最终送达 —— 保证在某个副本应用的每个更新最终会在所有副本上应用，
  • 以及 收敛性 —— 保证应用了相同更新的副本最终达到相同的状态。

使用在所有副本间不以相同顺序传递消息的广播协议，将不可避免地导致分歧（见图 11.4）。调和冲突写入的一种方法是使用共识来做出所有副本都需要同意的决定。

图 11.4: 同一对象被不同客户端在不同副本上同时更新，导致冲突。

与使用全序广播的方案相比，此解决方案具有更好的可用性和性能，因为共识仅用于调和冲突，并且可以在关键路径之外进行。但是，正确实现调和逻辑并非易事。那么，有没有办法让副本完全不用共识来解决冲突呢？

嗯，如果我们能为任何潜在的冲突定义一个确定性的结果（例如，时间戳最大的写入总是获胜），那么根据设计，就不会有任何冲突。因此，调和副本就不需要共识。这种复制策略提供了比普通最终一致性更强的保证，即：

  • 最终送达 —— 与最终一致性中的保证相同，
  • 以及 强收敛性 —— 保证执行了相同更新的副本拥有相同的状态（即，每个更新都立即持久化）。

这种最终一致性的变体也称为强最终一致性5。有了它，我们可以构建可用、（强最终）一致且分区容忍的系统。

保证副本强收敛需要哪些条件？例如，假设我们在 N 个副本之间复制一个对象，该对象是某种支持查询和更新操作的数据类型（例如，整数、字符串、集合等）的实例。

客户端可以向任何副本发送更新或查询操作，并且：

  • 当副本收到查询时，它立即使用对象的本地副本进行回复；
  • 当副本收到更新时，它首先将其应用到对象的本地副本，然后将更新后的对象广播给所有副本；
  • 当副本收到广播消息时，它将消息中的对象与其自身的对象合并。

可以证明，如果满足以下条件，每个副本将收敛到相同的状态：

  • 对象的可能状态形成一个半格，即一个包含可以部分排序的元素的集合；
  • 并且合并操作返回两个对象状态之间的最小上界（因此是幂等的、可交换的和可结合的）。

具有这些属性的数据类型也称为收敛复制数据类型6，它是无冲突复制数据类型（CRDTs）家族的一部分。这听起来比实际情况复杂得多。

例如，假设我们处理整数对象（可以部分排序），并且合并操作取两个对象的最大值（最小上界）。很容易看出，在这种情况下，即使请求在副本之间无序传递和/或多次传递，副本如何收敛到全局最大值。

尽管到目前为止我们假设使用了可靠的广播协议，但只要副本定期交换和合并它们的状态以确保最终收敛（也称为反熵机制，我们将在 11.3 节看到一些例子），它们甚至可以使用不可靠的协议来实现广播。当然，如果处理不当，定期的状态交换可能会代价高昂。

有许多数据类型在设计时考虑了复制时的收敛性，例如寄存器、计数器、集合、字典和图。例如，寄存器是一个存储某些不透明字节序列的内存单元，支持赋值操作以覆盖其状态。为了使寄存器收敛，我们需要在其值上定义一个偏序和一个合并操作。有两种常见的寄存器实现满足这些要求：最后写入者获胜（LWW）和多值（MV）。

一个最后写入者获胜寄存器为每次更新关联一个时间戳，使更新完全可排序。时间戳可以由一个Lamport时间戳（以保持更新之间的先发生关系）和一个副本标识符（以确保没有平局）组成。当副本收到来自客户端的更新请求时，它生成一个新的时间戳，并用该时间戳和新值更新寄存器的状态；最后，它将状态和时间戳广播给所有副本。当副本从对等方收到寄存器状态时，它通过取时间戳较大的那个并丢弃另一个来将其与本地副本合并（见图 11.5）。

图 11.5: 最后写入者获胜寄存器

LWW寄存器的主要问题是，通过取时间戳较大的那个来处理同时发生的冲突更新，这可能并不总是合理的。处理冲突的另一种方法是跟踪所有并发更新并将其返回给客户端应用程序，客户端应用程序可以按其认为合适的方式处理冲突。这就是多值寄存器采用的方法。为了检测并发更新，副本使用向量时钟时间戳7标记每个更新，合并操作返回所有并发更新的并集（见图 11.6）。

图 11.6: 多值寄存器

CRDTs的美妙之处在于它们可以组合。因此，例如，你可以通过使用LWW或MV寄存器的字典来构建一个收敛的键值存储。这就是Dynamo风格数据存储所采用的方法。

11.3 Dynamo风格的数据存储

Dynamo8可以说是最终一致且高可用的键值存储中最知名的设计。许多其他数据存储都受到了它的启发，例如Cassandra9和Riak KV10。

在Dynamo风格的数据存储中，每个副本都可以接受写入和读取请求。当客户端想要向数据存储写入一个条目时，它会并行地向所有N个副本发送请求，但只等待W个副本的确认（写入仲裁）。类似地，当客户端想要从数据存储读取一个条目时，它会向所有副本发送请求，但只等待R个回复（读取仲裁），并将最新的条目返回给客户端。为了解决冲突，条目的行为类似于LWW或MV寄存器，具体取决于实现方式。

当W + R > N时，写入仲裁和读取仲裁必须相互重叠，因此至少有一次读取会返回最新版本（见图11.7）。但这本身并不能保证线性一致性。例如，如果一次写入在少于W个副本上成功而在其他副本上失败，副本就会处于不一致的状态，一些客户端可能读取到最新版本，而另一些则不能。为了避免这种不一致性，写入操作需要捆绑在一个原子事务中。我们将在第12章中更多地讨论事务。

图 11.7: 重叠的写入与读取仲裁

通常，W和R被配置为多数仲裁，即包含超过半数副本的仲裁。也就是说，其他组合也是可能的，数据存储的读取和写入吞吐量取决于R和W的大小。例如，读取密集型工作负载受益于较小的R；然而，这会使写入变慢且可用性降低（假设W + R > N）。或者，为了在牺牲一致性（W + R < N）的情况下获得最大性能，可以将W和R都配置得非常小（例如，W = R = 1）。

这种方法的一个问题是，发送给副本的写入请求可能永远无法到达目的地。在这种情况下，无论等待多久，副本都无法收敛。为了确保副本收敛，使用了两种反熵机制：读取修复和副本同步。因此，思考仲裁复制的另一种方式是，它是一种最大努力广播，结合了反熵机制，以确保所有变更传播到所有副本。

读取修复是客户端实现的一种机制，用于在每次执行读取时帮助使副本恢复同步。如前所述，当客户端执行读取时，它会等待R个回复。现在，假设其中一些回复包含较旧的条目。在这种情况下，客户端可以向不同步的副本发出带有最新条目的写入请求。尽管这种方法对于频繁读取的条目效果很好，但不足以保证所有副本最终都会收敛。

副本同步是一种持续的后台机制，在每个副本上运行，并定期与其他副本通信以识别和修复不一致性。例如，假设副本X发现它拥有的键K的版本比副本Y的旧。在这种情况下，它将从Y检索K的最新版本。为了检测不一致性并最小化交换的数据量，副本可以通过八卦协议交换默克尔树哈希11。

11.4 CALM定理

此时，您可能想知道如何判断一个应用程序是否需要协调（例如共识），以及何时不需要。CALM定理12指出，一个程序当且仅当它是单调的时，才具有一致、无需协调的分布式实现。

直观地说，如果一个程序的新输入能进一步优化输出，并且不能撤回任何先前的输出，那么它就是单调的。计算集合并集的程序就是一个很好的例子——一旦一个元素（输入）被添加到集合（输出）中，它就无法被移除。类似地，可以证明CRDT是单调的。

相反，在非单调程序中，新的输入可以撤销先前的输出。例如，变量赋值就是一个非单调操作，因为它会覆盖变量之前的值。

单调程序可以同时实现一致性、可用性和分区容错性。然而，CALM中的一致性并非指线性一致性（即CAP定理中的C）。线性一致性狭义地关注读写的一致性。而CALM则关注程序输出的一致性13。在CALM中，一致的程序是指无论输入以何种顺序处理，也无论存在任何冲突，都能产生相同输出的程序；它并不涉及读写的一致性。

例如，假设您想实现一个计数器。如果您手头只有写入和读取操作，那么操作的顺序就至关重要：

write(1), write(2), write(3) => 3

但是：

write(3), write(1), write(2) => 2

相反，如果程序有一个支持递增操作的计数器抽象，您可以任意重新排序操作而不影响结果：

increment(1), increment(1), increment(1) => 3

换句话说，基于读写的一致性可能会限制解决方案的空间14，因为有可能构建在应用层面一致，但在存储层面的读写层面不一致的系统。

CALM也识别出那些由于非单调性而无法实现一致性的程序。例如，普通的寄存器/变量赋值操作不是单调的，因为它会使之前存储的任何值失效。但是，通过将赋值操作与逻辑时钟结合，可以构建一个单调的实现，正如我们之前在讨论LWW和MV寄存器时所看到的。

11.5 因果一致性

至此，我们理解了如何利用最终一致性来实现具备一致性、可用性和分区容错性的单调应用程序。遗憾的是，对于许多应用而言，其提供的保证并不充分。例如，最终一致性无法保证副本能以正确的顺序观察到那些存在先后发生关系的操作。假设你向社交网络上传了一张图片，然后将其添加到相册中。在最终一致性模型下，相册可能在图片可用之前就引用了它，从而导致显示一个缺失图片的占位符。

强一致性的主要优势之一在于它保持了操作之间的先后发生顺序，这保证了原因先于结果发生。因此，在前面的例子中，只有当图片可用之后，相册中对新添加图片的引用才会变得可见。

令人惊讶的是，为了保持操作之间的先后发生顺序（因果顺序），我们并不需要诉诸强一致性，因为我们可以使用一种称为因果一致性15的较弱一致性模型。该模型弱于强一致性但强于最终一致性，它特别吸引人有两个原因：

  • 对于许多应用来说，因果一致性“足够一致”，并且比最终一致性更易于处理。
  • 因果一致性被证明16是能够构建同时具备可用性和分区容错性系统的最强一致性模型。

因果一致性对操作施加了偏序关系。最简单的定义要求进程对因果相关操作的顺序达成一致，但对于不相关操作的顺序可以不一致。你可以取任意两个操作，要么一个先于另一个发生，要么它们是并发的，因此无法排序。这是与强一致性的主要区别，强一致性施加了一个所有进程都同意的全局顺序。

例如，假设一个进程更新了键值存储中的一个条目（操作A），随后另一个进程读取了该条目（操作B），并因此更新了另一个条目（操作C）。在这种情况下，系统中的所有进程都必须同意A先于C发生。相反，如果两个操作X和Y并发发生，且彼此没有先后发生关系，那么一些进程可能先观察到X后观察到Y，而另一些进程则可能先观察到Y后观察到X。

让我们看看如何利用因果一致性来构建一个在网络分区下仍可用的复制数据存储。我们将基于“保持顺序的服务器集群”（COPS17）展开讨论，这是一个在地理分布集群间提供因果一致性的键值存储。在COPS中，一个集群被设置为强一致性的分区数据存储，但为了简化，我们将其视为一个没有分区的单一逻辑节点。18 稍后，在第16章，我们将详细讨论分区。

首先，让我们定义一种因果一致性的变体，称为因果+，其中对于不相关操作的顺序不存在不一致（冲突）。不一致是有问题的，因为它们会导致副本永远分叉。为了避免这种情况，可以使用LWW寄存器作为值，以确保在存在并发写入时所有副本都能收敛到相同的状态。LWW寄存器由一个对象和一个逻辑时间戳组成，该时间戳代表其版本。

在COPS中，任何副本都可以接受读写请求，客户端将请求发送到离它们最近的副本（本地副本）。当客户端向其本地副本发送针对某个键的读取请求时，后者会回复本地可用的最新值。当客户端收到响应时，它会将接收到的值的版本（逻辑时间戳）添加到一个本地键-版本字典中，该字典用于跟踪依赖关系。

当客户端向其本地副本发送写入请求时，它会将依赖关系字典的副本附加到请求中。副本为该写入分配一个版本，在本地应用更改，并向客户端返回一个确认，其中包含分配给该写入的版本。即使在此期间其他客户端更新了该键，它也可以在本地应用更改，因为值是用LWW寄存器表示的。最后，更新被异步广播到其他副本。

当副本收到针对某个写入的复制消息时，它不会立即在本地应用。相反，它首先检查该写入的依赖项是否已在本地提交。如果没有，它会等待直到所需的版本出现。最后，一旦所有依赖项都已提交，复制消息才会在本地应用。这种行为保证了因果一致性（参见图11.8）。

图 11.8：一个键值存储的因果一致性实现

如果某个副本发生故障，数据存储仍然可用，因为任何副本都可以接受写入。存在一种可能性，即副本在本地提交更新后、但在广播之前发生故障，从而导致数据丢失。在COPS的情况下，为了避免在确认客户端写入之前等待一个或多个到远程副本的长距离请求所带来的代价，这种权衡被认为是可接受的。

11.6 实战考量

总而言之，在前面的章节中，我们探讨了实现复制的不同方法，并了解到一致性与可用性/性能之间存在权衡。换句话说，要构建可扩展且可用的系统，需要尽量减少协调工作。

这种权衡存在于任何大规模系统中，有些系统甚至提供了可调节的选项来让你控制它。例如，Azure Cosmos DB 是一个完全托管的可扩展 NoSQL 数据库，它允许开发人员在 5 种不同的一致性模型中进行选择，范围从最终一致性到强一致性19，其中较弱的一致性模型比较强的一致性模型具有更高的吞吐量。
