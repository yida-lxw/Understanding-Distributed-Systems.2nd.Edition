5 应用程序编程接口(API)

既然我们已经了解了客户端如何发现服务器的IP地址并与其建立可靠且安全的通信链路，那么接下来我们希望客户端能够调用服务器提供的操作。为此，服务器使用一个适配器——它定义了服务器的应用程序编程接口（API）——将接收自通信链路的消息转换为由其业务逻辑实现的接口调用（参见图1.2）。

客户端与服务器之间的通信方式可以是直接或间接的，这取决于客户端是直接与服务器通信，还是通过代理间接通信。直接通信要求两个进程都处于启动运行状态，通信才能成功。然而，有时这种保证并非必需或难以实现，在这种情况下，间接通信更为合适。间接通信的一个例子是消息传递。在此模型中，发送方和接收方不直接通信，而是通过消息通道（代理）交换消息。发送方向通道发送消息，而接收方则从通道读取消息。在后面的第23章中，我们将看到消息通道是如何实现的，以及如何最好地使用它们。

在本章中，我们将重点关注一种名为请求-响应的直接通信方式，即客户端向服务器发送请求消息，服务器则回复响应消息。这类似于函数调用，但跨越了进程边界并通过网络进行。

请求与响应消息中包含以语言无关格式序列化的数据。格式的选择决定了消息序列化与反序列化的速度、是否具备人类可读性，以及随时间演进的难易程度。文本格式（如JSON1）具备自描述性与人类可读性，但代价是冗长性增加与解析开销。另一方面，二进制格式（如Protocol Buffers2）相比文本格式更为精简且性能更高，但牺牲了人类可读性。

当客户端向服务器发送请求时，它可以阻塞并等待响应到达，使通信变得同步。或者，它也可以要求出站适配器在收到响应时调用回调函数，从而使通信变得异步。

同步通信效率低下，因为它会阻塞本可用于执行其他任务的线程。某些编程语言，如JavaScript、C#和Go，可以通过async/await等原语完全隐藏回调3。这些原语使得编写异步代码变得像编写同步代码一样简单明了。

常用于请求-响应交互的IPC技术包括HTTP和gRPC4。通常，组织内部用于服务器间通信的内部API会采用如gRPC这样的高性能RPC框架实现。相比之下，面向公众开放的外部API则倾向于基于HTTP构建，因为网络浏览器能通过JavaScript代码轻松发起HTTP请求。

一套广受欢迎的设计原则，用于设计优雅且可扩展的HTTP API，称为表述性状态转移（REST5），而基于这些原则的API则被称为RESTful。例如，这些原则包括：

  • 请求是无状态的，因此每个请求都包含处理它所需的所有必要信息；
  • 响应会被隐式或显式地标记为可缓存或不可缓存。如果一个响应是可缓存的，客户端可以在后续的等效请求中重用该响应。

鉴于RESTful HTTP API的普遍存在，我们将在本章的剩余部分逐步讲解创建HTTP API的过程。

5.1 HTTP

HTTP6 是一种请求-响应协议，用于在客户端和服务器之间编码和传输信息。在一次HTTP事务中，客户端向服务器的API端点发送一条请求消息，服务器则回复一条响应消息，如图5.1所示。

在HTTP 1.1中，消息是一个文本数据块，包含起始行、一组头部和一个可选的正文：

  • 在请求消息中，起始行指明了请求的目的；在响应消息中，它则表明请求是否成功。
  • 头部是描述消息元数据的键值对。
  • 消息正文是数据的容器。

图 5.1: 浏览器与Web服务器之间的HTTP事务示例

HTTP是一种无状态协议，这意味着服务器处理请求所需的一切信息都必须在请求本身中指定，而不依赖于先前请求的上下文。HTTP使用TCP来获得第2章讨论的可靠性保证。当它在TLS之上运行时，也被称为HTTPS。

HTTP 1.1默认保持与服务器的连接开放，以避免为下一次事务创建新连接。然而，在收到前一个请求的响应之前，无法发出新的请求（也称为队头阻塞或HOL阻塞）；换句话说，事务必须串行化。例如，浏览器需要获取多个图像来渲染HTML页面时，必须逐个下载它们，这可能非常低效。

尽管HTTP 1.1在技术上允许某些类型的请求进行流水线处理7，但它仍然受到HOL阻塞的影响，因为单个缓慢的响应会阻塞其后的所有响应。对于HTTP 1.1，提高出站请求吞吐量的典型方法是创建多个连接。然而，这是有代价的，因为连接会消耗内存和套接字等资源。

HTTP 28 从头开始设计，旨在解决HTTP 1.1的主要限制。它使用二进制协议而非文本协议，允许在同一连接上多路复用多个并发的请求-响应事务（流）。到2020年初，互联网上大约一半访问量最大的网站都在使用新的HTTP 2标准。

HTTP 39 是HTTP标准的最新版本，它基于UDP并实现了自己的传输协议，以解决TCP的一些缺点10。例如，在HTTP 2中，TCP连接上的数据包丢失会阻塞所有流（HOL），但在HTTP 3中，数据包丢失只会中断一个流，而不是所有流。

本书出于说明目的使用HTTP 1.1标准，因为其纯文本格式更易于展示。此外，HTTP 1.1仍然被广泛使用。

5.2 资源

假设我们想要实现一个服务来管理电子商务应用程序的产品目录。该服务必须允许客户浏览目录，并允许管理员创建、更新或删除产品。尽管这听起来很简单，但为了通过HTTP公开此服务，我们首先需要了解如何使用HTTP来构建API。

HTTP服务器托管资源，其中资源可以是物理或抽象的实体，例如文档、图像或其他资源的集合。URL通过描述资源在服务器上的位置来标识它。

在我们的目录服务中，产品集合就是一种资源类型，可以通过类似https://www.example.com/products?sort=price的URL来访问，其中：

  • https是协议；
  • www.example.com是主机名；
  • products是资源名称；
  • ?sort=price是查询字符串，它包含影响服务如何处理请求的附加参数；在本例中，它指定了响应中返回的产品列表的排序方式。

不带查询字符串的URL也被称为API的/products端点。

URL还可以构建资源之间的关系。例如，由于产品是属于产品集合的一种资源，具有唯一标识符42的产品可以拥有以下相对URL：/products/42。如果该产品还关联着一个评论列表，我们可以将评论的资源名称附加到产品URL之后，即/products/42/reviews。然而，随着资源嵌套层级的增加，API会变得更加复杂，因此需要权衡利弊。

为资源命名只是问题的一部分；当资源在请求和响应消息的正文中传输时，我们还必须在网络上对它们进行序列化。当客户端发送请求以获取资源时，它会在消息中添加特定的头部信息，以描述其偏好的资源表示形式。服务器使用这些头部信息来为响应选择最合适的表示形式11。通常，在HTTP API中，JSON用于表示非二进制资源。例如，/products/42的表示形式可能如下所示：

{
  "id": 42,
  "category": "Laptop",
  "price": 999
}

5.3 请求方法

HTTP 请求可以使用请求方法来创建、读取、更新和删除（CRUD）资源。当客户端向服务器请求特定资源时，它会指定要使用的方法。您可以将请求方法视为对资源使用的动词或操作。

最常用的方法是 POST、GET、PUT 和 DELETE。例如，我们的目录服务的 API 可以定义如下：

  • POST /products — 创建一个新产品并返回新资源的 URL。
  • GET /products — 检索产品列表。查询字符串可用于过滤、分页和排序集合。
  • GET /products/42 — 检索产品 42。
  • PUT /products/42 — 更新产品 42。
  • DELETE /products/42 — 删除产品 42。

请求方法可以根据其是否安全以及是否幂等来分类。一个安全的方法不应有任何可见的副作用，并且可以安全地被缓存。一个幂等的方法可以执行多次，最终结果应与只执行一次相同。幂等性是 API 的一个关键方面，我们将在后面的 5.7 节中详细讨论。

方法 安全 幂等
POST 否 否
GET 是 是
PUT 否 是
DELETE 否 是

5.4 响应状态码

服务器收到请求后，需要处理它并向客户端发送响应。HTTP响应包含一个状态码12，用于告知客户端请求是否成功。不同的状态码范围具有不同的含义。

200到299之间的状态码用于表示成功。例如，200 (OK) 表示请求成功，响应正文包含所请求的资源。

300到399之间的状态码用于重定向。例如，301 (Moved Permanently) 表示请求的资源已移动到响应消息Location头部中指定的另一个URL。

400到499之间的状态码保留给客户端错误。由于错误是由客户端而非服务器的问题引起的，因此以客户端错误而失败的请求如果重试，通常会返回相同的错误。因此，不应重试此类请求。一些常见的客户端错误有：

  • 400 (Bad Request) — 客户端输入验证失败。
  • 401 (Unauthorized) — 客户端未通过身份验证。
  • 403 (Forbidden) — 客户端已通过身份验证，但不允许访问该资源。
  • 404 (Not Found) — 服务器找不到请求的资源。

500到599之间的状态码保留给服务器错误。由于导致其失败的问题可能是暂时的，因此由于服务器错误而失败的请求可以重试。以下是一些典型的服务器状态码：

  • 500 (Internal Server Error) — 服务器遇到意外错误，无法处理请求。
  • 502 (Bad Gateway) — 服务器在充当网关或代理角色时，它会尝试访问其下游服务器来处理请求，但是收到了无效响应。13
  • 503 (Service Unavailable) — 由于临时过载或计划维护，服务器当前无法处理请求。

5.5 OpenAPI

既然我们已经理解了如何使用HTTP来构建API，那么我们就可以编写一个适配器，通过调用目录服务的业务逻辑来处理HTTP请求。例如，假设该服务由以下接口定义：

interface CatalogService
{
  List<Product> GetProducts(...);
  Product GetProduct(...);
  void AddProduct(...);
  void DeleteProduct(...);
  void UpdateProduct(...)
}

因此，当HTTP适配器收到一个GET /products请求以获取所有产品列表时，它将调用GetProducts(…)方法并将结果转换为HTTP响应。虽然这是一个简单的例子，但你可以看到适配器是如何将IPC机制（HTTP）连接到业务逻辑的。

我们可以通过使用接口定义语言（IDL）来定义服务的API，从而生成HTTP适配器的骨架。IDL是一种与语言无关的API定义，可用于生成服务器端适配器以及您所选语言的客户端软件开发工具包（SDK）的模板代码。

OpenAPI14规范源自Swagger项目，是RESTful HTTP API最流行的接口描述语言之一。通过它，我们可以在YAML文档中正式描述API，包括可用的端点、支持的请求方法、每个端点的响应状态码，以及资源JSON表示的结构。

例如，目录服务API的/products端点可以这样定义部分内容：

openapi: 3.0.0
info:
  version: "1.0.0"
  title: 目录服务 API

paths:
  /products:
    get:
      summary: 列出产品
      parameters:
        - in: query
          name: sort
          required: false
          schema:
            type: string
      responses:
        "200":
          description: 目录中的产品列表
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/ProductItem"
        "400":
          description: 错误的输入

components:
  schemas:
    ProductItem:
      type: object
      required:
        - id
        - name
        - category
      properties:
        id:
          type: number
        name:
          type: string
        category:
          type: string

尽管这是一个非常简单的示例，我们不会深入探讨OpenAPI，但它应该能让你对其表达能力有所了解。有了这个定义，我们就可以运行工具来生成API的文档、模板适配器和客户端SDK。

5.6 演进

一个API最初是一个精心设计的接口15。缓慢但必然地，它需要改变以适应新的用例。在演进API时，我们最不希望做的就是引入破坏性变更，这要求所有客户端必须立即修改，而其中一些客户端可能不在我们的控制范围内。

有两种类型的变更会破坏兼容性，一种在端点层面，另一种在消息层面。例如，如果我们将 /products 端点改为 /new-products，这显然会破坏那些尚未更新以支持新端点的客户端。同样，将一个原本可选的查询参数变为必填参数也会导致同样的问题。

以向后不兼容的方式更改请求或响应消息的结构也可能造成严重破坏。例如，将 Product 模式中 category 属性的类型从字符串改为数字，就是一个破坏性变更，会导致旧的客户端反序列化逻辑崩溃。对于使用其他序列化格式（如Protocol Buffers）表示的消息，也存在类似的论点16。

REST API应该进行版本控制以支持破坏性变更，例如，在URL中加上版本号前缀（/v1/products/）。然而，作为一个通用经验法则，除非有非常充分的理由，否则API应该以向后兼容的方式演进。尽管向后兼容的API往往不是特别优雅，但它们很实用。

5.7 幂等性

当API请求超时时，客户端无法得知服务器是否确实收到了该请求。例如，服务器可能已经处理了请求，却在将响应发送回客户端之前崩溃了。

客户端处理此类瞬时故障的一种有效方法是重试请求一次或多次，直到收到响应为止。一些HTTP请求方法（例如，PUT、DELETE）被认为是天生具有幂等性的，因为执行多个相同请求的效果与仅执行一个请求的效果相同17。例如，如果服务器连续两次处理针对同一资源的相同PUT请求，最终效果将与仅执行一次PUT请求相同。

但是，对于那些天生不具备幂等性的请求呢？例如，假设客户端发出一个POST请求，向目录服务添加一个新商品。如果请求超时，客户端无法知道请求是否成功。如果请求成功了，重试它将会创建两个相同的商品，这并非客户端的本意。

为了处理这种情况，客户端可能不得不实现某种协调逻辑，在重试请求时检查重复商品并将其删除。你可以看到这给客户端带来了多大的复杂性。与其将这种复杂性推给客户端，更好的解决方案是让服务器通过使POST请求具有幂等性来确保商品只被创建一次，这样无论该特定请求被重试多少次，其结果都如同只执行了一次。

为了让服务器能够检测出重复请求，需要为请求添加一个幂等键——一个唯一的标识符（例如，UUID）。该标识符可以作为请求头的一部分，就像Stripe API中的Idempotency-Key18。服务器为了检测重复请求，需要通过将其存储在数据库中来记住所有见过的请求标识符。当请求到达时，服务器检查数据库以查看该请求ID是否已存在。如果不存在，则将请求标识符添加到数据库并执行请求。请求标识符无需永久存储，可以在一段时间后清除。

现在，棘手的部分来了。假设服务器将请求标识符添加到数据库，但在执行请求之前崩溃了。在这种情况下，任何未来的重试都不会产生任何效果，因为服务器会认为它已经执行过了。因此，我们真正希望的是请求能够被原子性地处理：要么服务器成功处理请求并将请求标识符添加到数据库，要么处理失败且不存储请求标识符。

如果请求标识符和服务器管理的资源存储在同一个数据库中，我们可以通过ACID事务来保证原子性19。换句话说，我们可以在POST处理程序中，将商品创建和请求标识符记录包装在同一个数据库事务中。然而，如果处理程序需要调用其他外部服务来处理请求，实现就会变得更具挑战性20，因为这需要某种形式的协调。稍后，在第13.2章中，我们将学习如何做到这一点。

现在，假设服务器能够检测到重复请求，应该如何处理它呢？在我们的例子中，服务器可以用一个表示商品已存在的状态码来响应客户端。但这样一来，客户端就不得不以不同于收到第一个POST请求成功响应（201 Created）的方式来处理这种情况。因此，理想情况下，服务器应该返回与第一次请求完全相同的响应。

到目前为止，我们只考虑了单个客户端。现在，想象以下场景：

  1. 客户端A发送一个创建新商品的请求。虽然请求成功了，但客户端没有及时收到响应。
  2. 客户端B删除了新创建的商品。
  3. 客户端A重试最初的创建请求。

服务器应如何处理第3步中的请求？从客户端A的角度来看，收到最初的创建响应，比收到一个提及“使用该特定请求标识符创建的资源已被删除”的奇怪错误信息，更不容易让人感到意外21。当有疑问时，遵循最小意外原则是很有用的。

总而言之，幂等性API使得实现能够健壮应对故障的客户端变得容易得多，因为它们可以假设请求在失败时可以重试，而无需担心所有可能的边界情况。
