13 异步事务

2PC是一种同步阻塞协议——如果协调者或任何参与者响应缓慢或不可用，事务就无法继续推进。由于其阻塞特性，2PC通常与阻塞式并发控制协议（如2PL）结合使用以提供隔离性。这意味着参与者在等待协调者时会持有锁，从而阻塞其他访问相同对象的事务继续执行。

两阶段提交的基本假设是协调者和参与者都可用，并且事务的持续时间是短暂的。虽然我们可以通过使用状态机复制来解决参与者的可用性问题，但对于那些由于其本身天然需要长时间执行的事务，比如几个小时或几天，我们无能为力。在这种情况下，阻塞根本不是一个可行的选择。此外，如果参与者属于不同的组织，这些组织可能不愿互相授予权限，以阻止对方运行自己无法控制的事务。

为了解决这个问题，我们可以从现实世界中寻找解决方案。例如，考虑通过银行本票进行两家银行之间的资金转账。首先，签发支票的银行从源账户中扣除资金。然后，支票被物理运输到另一家银行，并最终存入目标账户。为了使资金转账成功，支票不能丢失或重复存入。由于在交易进行过程中，源银行和目标银行都不必相互等待，因此通过支票进行的资金转账是一种异步（非阻塞）原子事务。然而，为此付出的代价是，在支票转移期间，源账户和目标账户处于不一致的状态。因此，尽管异步事务是原子的，但它们彼此之间并不隔离。

现在，由于检查本质上只是一种消息，我们可以通过持久化网络消息的概念来推广这一思想，即确保消息能够被恰好一次处理。在本章中，我们将讨论基于此概念的几种异步事务实现。

13.1 发件箱模式

现代应用程序中的一个常见模式1是将相同的数据复制到针对不同用例定制的不同数据存储中。例如，假设我们拥有一个由关系数据库支持的产品目录服务，并且我们决定在其API中提供高级全文搜索功能。虽然一些关系数据库提供基本的全文搜索功能，但对于更高级的用例，则需要像Elasticsearch2这样的专用服务。

为了与搜索服务集成，当添加新产品、修改或删除现有产品时，目录服务需要同时更新关系数据库和搜索服务。服务可以先更新关系数据库，然后再更新搜索服务，但如果服务在更新搜索服务之前崩溃，系统将处于不一致的状态。因此，我们需要以某种方式将这两个更新包装到一个事务中。

我们可以考虑使用2PC，但是虽然关系数据库支持X/Open XA3 2PC标准，搜索服务却不支持，这意味着我们必须以某种方式为搜索服务实现该协议。我们也不希望因为搜索服务暂时不可用而导致目录服务阻塞。尽管我们希望两个数据存储保持同步，但我们可以接受一些暂时的不一致。因此，最终一致性对我们的用例来说是可以接受的。

我们可以通过让目录服务在添加、修改或删除产品时向搜索服务发送持久化消息来解决这个问题。一种实现方式是，当本地事务对产品目录进行更改时，将消息追加到一个专用的发件箱表4中。因为关系数据库支持ACID事务，所以消息被追加到发件箱表中当且仅当本地事务提交且未被中止。

然后，发件箱表可以由一个专用的中继进程进行监控。当中继进程发现新消息时，它会将消息发送到目的地，即搜索服务。中继进程只有在收到消息已成功送达的确认后，才会从表中删除该消息。不出所料，同一条消息有可能被多次送达。例如，如果中继进程在发送消息之后、从表中删除消息之前崩溃，那么它在重启时会重新发送该消息。为了保证目的地只处理一次消息，会为其分配一个幂等键，以便对消息进行去重处理（我们在5.7章讨论过这一点）。

在实践中，中继进程并不直接将消息发送到目的地。相反，它将消息转发到一个消息通道5，例如Kafka6或Azure Event Hubs7，该通道负责按照消息被追加的顺序将它们送达一个或多个目的地。在后面的23章中，我们将更详细地讨论消息通道。

如果你稍微眯眼看看，你会发现我们在这里实现的方案在概念上类似于状态机复制，其中状态由目录中的产品表示，而复制是通过操作日志（发件箱表）进行的。

13.2 Saga模式

现在假设我们运营一个旅行预订服务。为了预订一次旅行，该旅行服务必须原子性地通过一个专用服务预订航班，并通过另一个服务预订酒店。然而，这两个服务中的任何一个都可能使其各自的请求失败。如果一个预订成功，但另一个失败，那么前者需要被取消以保证原子性。因此，预订一次旅行需要多个步骤来完成，其中一些步骤仅在失败情况下才需要执行。基于这个原因，我们不能使用前面介绍的简单解决方案。

Saga8 模式为这个问题提供了一个解决方案。一个saga是由一组本地事务 T1,T2,...,TnT_1, T_2, ..., T_n 组成的分布式事务，其中每个 TiT_i 都有一个对应的补偿性本地事务 CiC_i，用于撤销其更改。Saga保证要么所有本地事务都成功，要么在发生故障时，补偿性本地事务会完全撤销事务的部分执行。这保证了协议的原子性；要么所有本地事务都成功，要么一个都不成功。

理解saga的另一种方式是：每个本地事务 TiT_i 都假设所有其他本地事务会成功。这是一种猜测，而且很可能是一个好的猜测，但归根结底仍然是一种猜测。所以当猜测错误时，就犯了一个错误，需要以补偿事务 CiC_i 的形式发出一个“道歉9”。这类似于现实世界中发生的情况，例如航班超额预订。

Saga可以通过一个编排器（即事务协调器）来实现，该编排器管理跨相关进程（即事务参与者）的本地事务的执行。在我们的例子中，旅行预订服务是事务协调器，而航班和酒店预订服务是事务参与者。该saga由三个本地事务组成：T1T_1 预订航班，T2T_2 预订酒店，C1C_1 取消由 T1T_1 预订的航班。

从宏观层面来看，该saga可以用图 13.1 中描述的 工作流10 来实现：

  1. 协调器通过向航班服务发送预订请求（T1T_1）来启动事务。如果预订失败，没有造成损害，协调器将事务标记为已中止。
  2. 如果航班预订成功，协调器向酒店服务发送预订请求（T2T_2）。如果请求成功，事务被标记为成功，我们就完成了。
  3. 如果酒店预订失败，事务需要中止。协调器向航班服务发送取消请求（C1C_1）以取消先前预订的航班。如果没有取消操作，事务将处于不一致的状态，这将破坏其原子性保证。

协调器可以通过消息通道与参与者进行异步通信，以容忍临时故障。由于事务需要多个步骤才能成功，并且协调器可能在任何时间点发生故障，它需要在事务推进时持久化事务的状态。通过将事务建模为状态机，协调器可以在从一个状态转换到下一个状态时，将其状态持久地检查点保存到数据存储中。这确保了如果协调器崩溃并重启，或者另一个进程被选为协调器，它可以通过读取最后一个检查点来从上次中断的地方恢复事务。

图 13.1: 实现异步事务的工作流

不过，有一个需要注意的地方：如果协调器在发送请求之后、备份其状态之前崩溃，当它重新上线时，会再次发送相同的请求。同样，如果发送请求超时，协调器将不得不重试，导致消息在接收端出现两次。因此，参与者必须对接收到的消息进行去重，使其具有幂等性。

在实践中，您不需要从头开始构建编排引擎来实现此类工作流，因为像 AWS Step Functions11 或 Azure Durable Functions12 这样的云计算服务使得创建托管工作流变得很容易。

13.3 隔离性

我们开始探索异步事务之旅，是为了规避两阶段提交（2PC）的阻塞特性。但为了实现这一点，我们不得不牺牲传统ACID事务提供的隔离性保证。事实证明，我们同样可以设法应对隔离性的缺失。例如，一种方法是使用语义锁13。其核心思想是，saga修改的任何数据都会被标记一个脏标志，该标志仅在事务结束时才被清除。另一个试图访问带有脏标志记录的事务，要么会失败并回滚其更改，要么必须等待脏标志被清除。
