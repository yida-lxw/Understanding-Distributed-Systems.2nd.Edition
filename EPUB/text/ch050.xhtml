31 监控

监控主要用于检测影响生产环境中用户的故障，并向负责系统的人工操作员触发通知（或告警）。监控的另一个重要用例是通过仪表盘提供系统健康状况的高级概览。

在早期，监控主要用于报告服务是否正常运行，而对其内部运行状况缺乏足够的可见性（黑盒监控）。随着时间的推移，开发人员也开始在他们的应用程序中植入代码，以报告特定功能是否按预期工作（白盒监控）。随着Etsy引入statsd1，这种做法得以普及，它规范了应用层指标的收集。虽然黑盒监控有助于检测故障的表象，而白盒监控则能帮助定位根本原因。

黑盒监控的主要应用场景是监控外部依赖项，例如第三方API，并从用户视角验证服务的性能与健康状况。一种常见的黑盒方法是定期运行测试脚本（合成监控2），这些脚本向外部API端点发送测试请求，并监控其耗时与是否成功。合成监控部署在与应用程序用户相同的地理区域，并访问用户所使用的相同接口端点。因为它从外部检测系统对外暴露的接口，因此能够发现内部监控无法察觉的问题，例如网络连接故障。此外，合成监控对于检测那些用户极少访问的 API 所存在的问题也十分有效。

例如，如果某个服务的DNS服务器宕机，合成监控会立即发现问题，因为它们无法解析该服务的IP地址。然而，服务自身会认为一切正常，只是感觉接收到的请求量比平时少。

31.1 指标

指标指的是资源使用情况（例如，CPU利用率）或行为（例如，失败的请求数量）的原始测量值（样本）的时间序列，其中每个样本由一个浮点数和一个时间戳表示。

通常，一个指标还可以用一组键值对（标签）进行标记。例如，标签可以表示服务运行所在的区域、数据中心、集群或节点。标签使得对数据进行切片和切块变得容易，并消除了为每个标签组合手动创建指标所需的埋点成本。然而，由于每个不同的标签组合都是一个不同的指标，标记会生成大量指标，使得存储和处理它们变得更具有挑战性。

至少，服务应该发出关于其负载（例如，请求吞吐量）、其内部状态（例如，内存缓存大小）及其依赖项的可用性和性能（例如，数据存储响应时间）的指标。结合下游服务发出的指标，这使运维人员能够快速识别问题。但这需要显式的代码更改和开发人员主动投入精力对其代码进行埋点。

例如，以一个返回资源的虚构HTTP处理器为例。一旦它在生产环境中运行，我们将希望能够回答一系列问题3：

def get_resource(id):
  resource = self._cache.get(id)  # 进程内缓存
  # id参数是否合法?
  # 这里缓存是否命中?
  # 该资源在缓存中存放了多长时间？?

  if resource is not None:
    return resource

  resource = self._repository.get(id)
  # 远程调用是否失败？如果是，为什么呢?
  # 远程调用是否超时?
  # 远程调用需要耗时多久?

  self._cache[id] = resource
  # 这个缓存的大小是多少?

  return resource
  # 这个handler运行需要耗时多久?

现在，假设我们想要记录处理器未能处理的请求数量。一种方法是采用基于事件的方法——每当处理器未能处理请求时，它就在一个事件4中向本地遥测代理报告失败计数为1，例如：

{
  "failureCount": 1,
  "serviceRegion": "EastUs2",
  "timestamp": 1614438079
}

代理将这些事件批量处理，并定期将它们发送到远程遥测服务，该服务将它们持久化在专门用于事件日志的数据存储中。例如，这正是Azure Monitor基于日志的指标5所采用的方法。

可以想象，这成本相当高，因为遥测服务的负载随着摄取的事件数量增加而增加。在查询时聚合事件的成本也很高——假设我们想要检索过去一个月北欧的故障数量；我们将不得不发起一个查询，需要在该时间段内获取、过滤和聚合可能数万亿的事件。

那么，有没有办法降低查询时的成本呢？因为指标是一种时间序列，所以可以用数学工具对它们进行建模和处理。例如，时间序列样本可以在固定的时间段（例如，1分钟、5分钟、1小时等）内进行预聚合，并用汇总统计信息（如总和、平均值或百分位数）表示。

回到我们的例子，遥测服务可以在摄取时预聚合故障计数事件。如果聚合（即我们例子中的总和）以一小时为周期进行，那么每个serviceRegion将有一个failureCount指标，每个指标每小时包含一个样本，例如：

"00:00", 561,
"01:00", 42,
"02:00", 61,
...

摄取服务还可以创建具有不同周期的多个预聚合。这样，在查询时可以选择满足查询且具有最佳周期的预聚合指标。例如，CloudWatch6（AWS使用的遥测服务）在数据被摄取时对其进行预聚合。

我们可以更进一步，通过让本地遥测代理在客户端预聚合指标来降低摄取成本。通过结合客户端和服务器端的预聚合，我们可以大幅减少指标的带宽、计算和存储需求。然而，这需要付出代价的：我们失去了在摄取后重新聚合指标的能力，因为我们不再能够访问生成它们的原始事件。例如，如果一个指标在1小时的周期内进行了预聚合，那么在没有原始事件的情况下，以后就无法在5分钟的周期内重新聚合。

由于指标主要用于告警和可视化目的，它们通常以预聚合的形式持久化在专门用于高效时间序列存储的数据存储中7。

31.2 服务级别指标

如前所述，指标的主要用途之一是告警。但这并不意味着我们应该为每一个可能的指标都创建告警——例如，在半夜由于某个服务几分钟前内存使用量出现巨大峰值而被告警吵醒，这是毫无意义的。

在本节中，我们将讨论一个特别适合用于告警的特定指标类别：服务级别指标。SLI 是一种度量指标，用于衡量服务向其用户提供的服务水平的某个方面，例如响应时间、错误率或吞吐量。SLI 通常在一个滚动时间窗口内聚合，并用一个汇总统计量（如平均值或百分位数）来表示。

SLI 最好定义为两个指标的比率："良好事件"的数量除以事件总数。这使得该比率易于解释：0 表示服务完全故障，1 表示被测量的内容按预期正常工作（参见图 31.1）。正如我们将在本章后面看到的那样，比率也简化了告警的配置。服务中一些常用的 SLI 包括：

  • 响应时间 —— 在给定阈值内完成的请求所占的比例。
  • 可用性 —— 服务可用的时间比例，定义为成功请求数除以总请求数。

图 31.1：SLI 定义为良好事件数量与事件总数的比率

一旦我们决定了要测量什么，就需要决定在哪里测量。以响应时间为例。我们应该从服务、负载均衡器还是客户端的角度来测量响应时间？理想情况下，我们应该选择最能代表用户体验的指标。如果收集成本太高，我们应该选择次优的方案。在前面的例子中，客户端指标是其中最有意义的，因为它考虑了整个请求路径中的延迟和突发问题。

那么，我们应该如何测量响应时间呢？测量可能受到许多因素的影响，例如网络延迟、页面错误或大量的上下文切换。由于每个请求花费的时间并不相同，响应时间最好用分布(特指数学中的概率分布或统计分布)来表示，这种分布通常呈现右偏且长尾8的特征。

分布可以用一个统计量来概括。以平均值为例。虽然它有其用途，但它并不能告诉我们有多少比例的请求经历了特定的响应时间，而且只需要一个大的异常值就会扭曲平均值。例如，假设我们收集了 100 个响应时间，其中 99 个是 1 秒，1 个是 10 分钟。在这种情况下，平均值接近 7 秒。因此，尽管 99% 的请求响应时间为 1 秒，平均值却是它的 7 倍。

表示响应时间分布的更好方法是使用百分位数。百分位数是指低于该值的响应时间所占的百分比。例如，如果第 99 百分位数是 1 秒，那么 99% 的请求的响应时间小于或等于 1 秒。响应时间分布的高百分位数，如第 99 和第 99.9 百分位数，也被称为长尾延迟。尽管只有一小部分请求会经历这些极端延迟，但它可能会影响业务中最重要的用户。他们是发出最多请求的用户，因此更有可能遇到尾部延迟。有研究9表明，高延迟会对收入产生负面影响：仅仅 100 毫秒的加载时间延迟就可能导致转化率下降 7%。

此外，长尾延迟会对服务产生巨大影响。例如，假设一个服务平均使用约 2K 个线程来每秒处理 10K 个请求。根据利特尔法则10，线程的平均响应时间为 200 毫秒。现在，如果突然有 1% 的请求开始需要 20 秒才能完成（例如，由于交换机拥塞和超时设置宽松），那么仅处理这些慢请求就需要额外 2K 个线程。因此，服务使用的线程数必须翻倍才能维持负载！

测量并控制长尾延迟不仅能让我们的用户满意，还能极大地提高我们系统的弹性，同时降低其运营成本。直观地说，通过减少长尾延迟（最坏情况），我们同时也改善了平均情况。

31.3 服务级别目标

服务级别目标（SLO）定义了服务级别指标（SLI）的可接受值范围，在此范围内服务被视为处于健康状态（参见图 31.2）。SLO向服务的用户设定了服务在正常运行时应如何表现的期望。服务所有者还可以使用SLO与用户定义服务级别协议（SLA）——这是一份合同协议，规定了当SLO未达到时会发生什么，通常会涉及经济责任。

例如，一个SLO可以定义为：在为期一周的滚动窗口期内，对端点X的API调用应有99%在200毫秒内完成。另一种理解方式是：在滚动的一周内，最多有1%的请求延迟高于200毫秒是可以接受的。这1%也被称为错误预算，它代表了可以容忍的故障数量。

图 31.2: SLO定义了SLI的可接受值范围。

SLO既能有效支持告警，又能帮助团队优先处理修复任务。例如，团队可以约定，当错误预算耗尽时，修复事项将优先于新功能，直到SLO得到修复。此外，一个事件的重要性可以通过其消耗了多少错误预算来衡量。例如，一个消耗了20%错误预算的事件比只消耗了1%的事件更重要。

较短的时间窗口迫使团队更快地采取行动，并优先处理bug修复和修复事项，而较长的窗口则更适合就投资哪些项目做出长期决策。因此，拥有多个具有不同窗口大小的SLO是有意义的。

SLO应该设定得多严格？选择合适的目标范围，其难度远超表面所见。如果太宽松，我们将无法检测到面向用户的问题；如果太严格，工程时间将浪费在收益递减的微观优化上。即使我们能够保证系统100%的可靠性（这是不可能的），我们也无法对用户访问服务所依赖的、且超出我们控制范围的环节做出保证，例如用户的“最后一公里”网络连接。因此，100%的可靠性并不能转化为用户100%可靠的体验。

在为SLO设定目标范围时，合理的做法是从宽松的范围开始，随着我们建立信心再逐步收紧。我们不应该仅仅选择当前服务能够达到的目标，这些目标可能在负载增加一年后变得无法实现。相反，我们应该从用户关心的角度出发进行逆向推导。一般来说，实现超过三个9的可用性成本非常高，并且收益递减。

此外，我们应力求保持简洁，仅保留足够反映预期服务水准的最少数量的服务级别目标（SLO），并定期对其进行审查。例如，若发现某个面向用户的问题引发了大量支持工单，但所有现有SLO均未显示任何性能劣化，则说明这些SLO可能设定得过于宽松，或未能覆盖特定的使用场景。

SLO需要与多个利益相关者达成一致。如果错误预算消耗过快或已经耗尽，修复事项必须优先于功能开发。工程师需要同意这些目标是可以实现的，而无需付出过度的辛劳。产品经理也必须同意这些目标能保证良好的用户体验。正如谷歌的SRE书中所提到的11：“如果你永远无法通过引用某个特定的SLO来赢得关于优先级的讨论，那么这个SLO可能就不值得拥有。”

值得一提的是，用户可能会过度依赖我们服务的实际行为，而不是其文档化的SLA。为了防止这种情况，我们可以在生产环境中定期注入受控故障12——这也被称为混沌测试。这些受控故障确保系统依赖具备应对目标服务级别的能力，并且不做不切实际的假设。此外，它们还能验证弹性机制是否按预期工作。

31.4 告警

告警是监控系统的一部分，当特定条件发生时（例如某个指标超过阈值），它会触发一个动作。根据告警的严重程度和类型，动作的范围可以从运行一些自动化操作（例如重启服务实例），到呼叫值班运维人员的电话。在本节的其余部分，我们将主要关注后一种情况。

为使告警真正有效，它必须是可操作的。运维人员不应花费时间探索仪表盘来评估告警的影响和紧急程度。例如，一个指示CPU使用率激增的告警是无用的，因为如果不进行进一步调查，就不清楚它是否对系统有任何影响。另一方面，SLO是告警的一个良好候选，因为它量化了对用户的影响。可以监控SLO的错误预算，每当其大部分被消耗时触发告警。

在讨论如何定义告警之前，重要的是要理解其精确率和召回率之间存在权衡取舍关系。严格上来说，精确率是重要事件（即实际问题）占告警总数的比例，而召回率是触发告警的重要事件的比率。精确率低的告警嘈杂且通常不可操作，而召回率低的告警在故障期间并不总是触发。虽然拥有100%的精确率和召回率会很好，但提高其中一个通常会降低另一个，因此需要做出妥协。

假设我们有一个30天内可用性为99%的SLO，并希望为其配置告警。一种简单的方法是，只要可用性在相对较短的时间窗口（例如一小时）内低于99%，就触发告警。但是，当告警触发时，实际上已经消耗了多少错误预算？因为告警的时间窗口是一小时，而SLO错误预算是在30天内定义的，所以告警触发时已花费的错误预算百分比为 1小时30天=0.14%\frac{\text{1小时}}{\text{30天}} = 0.14\%。系统永远不会100%健康，因为在任何给定时间总会有一些故障。因此，被告知SLO错误预算的0.14%已被消耗是无用的。在这种情况下，我们拥有高召回率但低精确率。

我们可以通过增加条件需要成立的时间量来提高告警的精确率。问题是，现在告警需要更长的时间才能触发，即使在实际故障期间也是如此。另一种方法是基于错误预算消耗的速度（也称为燃烧率）进行告警，这降低了检测时间。燃烧率定义为已消耗的错误预算百分比与已过去的SLO时间窗口百分比之比值——它是错误预算的消耗速率。因此，使用我们之前的例子，燃烧率为1意味着错误预算将在30天内耗尽；如果速率为2，则将是15天；如果速率为3，则将是10天，依此类推。

为了提高召回率，我们可以设置具有不同阈值的多个告警。例如，燃烧率低于2可以被归类为低严重性告警，在工作时间内进行调查，而燃烧率超过10则可以触发对工程师的自动呼叫。SRE工作手册中有一些很好的例子13，说明了如何基于燃烧率配置告警。

尽管大多数告警应该基于SLO触发，但有些告警应该基于我们尚未有时间设计或通过调试消除掉的已知故障模式来触发。例如，假设我们已知某个服务存在内存泄漏，过去曾导致过事故，但我们尚未设法追踪到根本原因。在这种情况下，作为一种临时缓解措施，我们可以定义一个告警，当服务实例内存不足时触发自动重启。

31.5 仪表盘

除了告警之外，指标的另一个主要用途是增强实时仪表盘的表现力，以直观呈现系统的整体健康状况。遗憾的是，仪表盘很容易变成图表的垃圾场，这些图表最终会被遗忘、用处存疑，或者干脆令人困惑。好的仪表盘并非偶然产生。在本节中，我们将讨论创建有用仪表盘的一些最佳实践。

创建仪表盘时，我们首先要做的决定是确定受众是谁14以及他们需要什么。然后，根据受众，我们可以逆向决定包含哪些图表，进而决定包含哪些指标。

这里介绍的仪表盘类别（参见图 31.3）绝非标准，但应该能让您了解如何组织仪表盘。

图 31.3: 仪表盘应根据其受众进行定制。

SLO 仪表盘

SLO 摘要仪表盘旨在供组织内各利益相关方使用，以通过 SLO 了解系统健康状况。在事件期间，此仪表盘可量化事件对用户造成的影响。

公共 API 仪表盘

此仪表盘显示有关系统公共 API 端点的指标，有助于运维人员在事件期间识别有问题的路径。对于每个端点，仪表盘会暴露与请求消息、请求处理和响应消息相关的若干指标，例如：

  • 接收到的请求数或从消息代理拉取的消息数、请求大小统计信息、身份验证问题等。
  • 请求处理时长、外部依赖项的可用性和响应时间等。
  • 每种响应类型的计数、响应大小等。

服务仪表盘

服务仪表盘显示特定于服务的实现细节，这需要深入了解其内部工作原理。与之前的仪表盘不同，此仪表盘主要由拥有该服务的团队使用。除了特定于服务的指标外，服务仪表盘还应包含上游依赖项（如负载均衡器和消息队列）以及下游依赖项（如数据存储）的指标。

在调试时，此仪表盘提供了了解服务内部情况的第一入口。正如我们稍后在讨论可观测性时将了解到的，这种宏观视图只是起点。运维人员通常会通过进一步细分指标来深入探究，并最终查看原始日志和跟踪以获取更多详细信息。

31.5.1 最佳实践

随着新指标的添加和旧指标的移除，图表和仪表盘需要修改并在多个环境（例如预生产环境和生产环境）中保持同步。实现这一目标的最有效方法是使用领域特定语言定义仪表盘和图表，并像代码一样对其进行版本控制。这使得仪表盘可以通过包含相关代码更改的同一个拉取请求进行更新，而无需手动更新仪表盘，后者容易出错。

由于仪表盘自上向下渲染，最重要的图表应始终位于最顶部。此外，图表应使用默认时区（如 UTC）渲染，以便位于世界不同地区的人员在查看相同数据时便于沟通。

同一仪表盘中的所有图表应使用相同的时间分辨率（例如 1分钟、5分钟、1小时等）和范围（24小时、7天等）。这使得在同一仪表盘中直观地关联图表间的异常变得容易。我们可以根据仪表盘最常见的用例选择默认时间范围和分辨率。例如，1小时范围和1分钟分辨率最适合监控正在发生的事件，而1年范围和1天分辨率最适合容量规划。

我们应将同一图表上的数据点和指标数量保持在最低限度。渲染过多数据点不仅会使图表下载/渲染速度变慢，还会使图表难以解读以及难以发现异常情况。。

一个图表应仅包含具有相似范围（最小值和最大值）的指标；否则，范围最大的指标可能会完全掩盖范围较小的其他指标。因此，将同一指标的相关统计数据拆分为多个图表是有意义的。例如，一个指标的第10百分位数、平均值和第90百分位数可以显示在一个图表中，而第0.1百分位数、第99.9 百分位数、最小值和最大值则显示在另一个图表中。

图表还应包含有用的注释，例如：

  • 图表描述，并附有运行手册、相关仪表盘和升级联系人的链接；
  • 每个已配置告警阈值（如果有）的水平线；
  • 每个相关部署的垂直线。

仅在错误条件发生时发出的指标可能难以解读，因为图表会在数据点之间显示较大的间隙，让运维人员怀疑服务是否因错误而停止发出该指标。为避免这种情况，最佳实践是在没有错误时使用零值发出指标，在存在错误时使用值 1 发出指标。

31.6 值班待命

只有从一开始就将可靠性和可操作性纳入考量来构建服务，才有可能建立健康的待命轮值制度。让开发者对他们构建的系统负责运维，会激励他们将运维负担降至最低。同时，他们也是最适合值班待命的人选，因为他们对系统的架构、瓶颈和权衡取舍了如指掌。

值班待命可能带来巨大压力。即使没有呼叫，仅仅是想到在常规工作时间之外失去通常的自由，也可能引发强烈的焦虑感。因此，值班工作应当获得相应补偿，并且不应期望值班工程师在功能开发方面取得任何进展。既然他们会被告警打断，就应该充分利用这段时间，并给予他们充分的自由来改善值班体验，例如，修订仪表盘或改进弹性机制。

只有当告警具有可操作性时，才能实现健康的待命轮值。告警触发时，至少应链接到相关的仪表盘和一份操作手册，其中列出工程师应采取的行动15。除非告警是误报，否则运维人员采取的所有行动都应通报到一个共享渠道，例如其他团队也能访问的全局聊天室。这允许其他工程师参与进来，跟踪事件进展，并更容易地将进行中的事件移交给他人。

处理告警的第一步是缓解它，而不是修复引发告警的根本原因。新部署的构件导致服务性能下降？回滚它。服务无法应对负载，即使负载并未增加？横向扩展它。

一旦事件得到缓解，下一步就是理解根本原因，并找出防止其再次发生的方法。根据服务级别目标（SLO）衡量的影响越大，我们在这方面投入的时间就应该越多。消耗了SLO错误预算显著比例的事件，需要进行正式的事后复盘。事后复盘的目标是理解事件的根源，并制定一系列修复项以防止其再次发生。理想情况下，团队内部还应达成共识：如果某个SLO的错误预算耗尽或告警数量失控，整个团队应停止开发新功能，专注于可靠性工作，直到恢复健康的待命轮值状态。
