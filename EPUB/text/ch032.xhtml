19 数据存储

由于Cruder是无状态的，我们能够通过在负载均衡器后运行多个应用服务器来扩展它。但随着应用处理更多负载，对关系型数据库的请求数量也随之增加。由于数据库托管在单台机器上，达到其容量并开始性能下降只是时间问题。

19.1 复制

我们可以通过创建副本（replica）来提升数据库的读取能力。最常见的方法是采用主从（leader-follower）拓扑结构（参见图19.1）。在这种模型中，客户端将写操作（更新、插入和删除）专门发送给主节点（leader），主节点将这些变更持久化到其预写日志（write-ahead log）中。然后，从节点（follower）或副本连接到主节点，并从中流式传输日志条目，在本地提交这些条目。由于日志条目具有序列号，从节点可以随时断开连接并重新连接，并通过向主节点告知其最后处理的序列号，从上次中断的位置继续同步。

图 19.1: 单主复制

通过创建只读从节点并将其置于负载均衡器之后，我们可以提升数据库的读取能力。复制还能提高数据库的可用性。例如，当负载均衡器检测到某个副本不再健康或不可用时，可以自动将其从池中移除。而当主节点发生故障时，可以重新配置一个副本来接替其位置。此外，单独的从节点可用于隔离特定的工作负载，例如定期运行的昂贵分析查询，从而避免它们影响主节点和其他副本。

主节点与从节点之间的复制可以是完全同步的、完全异步的，或者是两者的结合。

如果复制是完全异步的，当主节点接收到一个写操作时，它会将其广播给从节点，并立即向客户端返回响应，而无需等待从节点的确认。尽管这种方法最大限度地减少了客户端的响应时间，但它不具备容错能力。例如，主节点可能在确认一个写操作之后、但在将其广播给从节点之前崩溃，从而导致数据丢失。

相反，如果复制是完全同步的，主节点会等待从节点确认写操作后，才向客户端返回响应。这会带来性能开销，因为任何一个缓慢的副本都会增加每个请求的响应时间。并且，如果任何副本不可达，数据存储就会变得不可用。这种方法不具备可扩展性；从节点越多，至少有一个从节点缓慢或不可用的可能性就越大。

在实战中，关系型数据库通常支持同步和异步复制相结合的方式。例如，在 PostgreSQL 中，可以配置单个从节点以同步方式接收更新1，而不是默认的异步方式。因此，举例来说，我们可以有一个同步从节点，其目的是作为主节点的实时备份。这样，如果主节点发生故障，我们可以故障转移到该同步从节点，而不会造成任何数据丢失。

从概念上讲，故障转移机制需要：检测主节点何时发生故障；将同步从节点提升为新的主节点，并重新配置其他副本以跟随它；确保客户端请求被发送到新的主节点。托管解决方案如 AWS RDS 或 Azure SQL Database，开箱即用地支持只读副本2和自动故障转移3，以及其他功能如自动补丁和备份。

复制的一个注意事项是，它仅有助于读取操作扩容，而不是写入操作。另一个问题是整个数据库需要能够容纳在单台机器上。尽管我们可以通过将一些表从主数据库移动到运行在不同节点上的其他数据库来规避这个问题，但这只是延迟了不可避免的情况。正如你现在应该知道的，我们可以通过分区来克服这些限制。

19.2 分区

分区使我们能够扩展数据库以支持读写操作。尽管传统（集中式）的关系数据库通常不直接支持此功能，但原则上我们可以在应用层实现它。然而，在应用层实现分区具有挑战性，并且会给系统增加大量复杂性。首先，我们需要决定如何在数据库实例之间划分数据，并在分区变得过于热门或过大时重新平衡数据。一旦数据被分区，跨越多个分区的查询就需要被拆分为子查询，并且它们的响应必须被合并（例如聚合或连接操作）。此外，为了支持跨分区的原子事务，我们需要实现分布式事务协议，如2PC。再加上需要将分区与复制相结合的要求，你可以看到在应用层实现分区变得多么艰巨。

退一步讲，传统关系数据库的根本问题在于它们的设计假设是能够运行在单个高性能机器上。正因为如此，它们支持许多难以扩展的特性，例如ACID事务和连接操作。关系数据库设计于磁盘空间昂贵的时代，当时优先考虑的是规范化数据以减少磁盘占用，即使这会在查询时通过连接操作反规范化数据带来显著的成本。4

时代已经改变，如今存储变得廉价，而CPU时间则不然。这就是为什么在21世纪初，大型科技公司开始构建定制化的数据存储解决方案，这些方案从一开始就被设计为具有高可用性和可扩展性。

19.3 NoSQL

这些早期的解决方案不支持SQL，通常它们只实现了传统关系型数据存储所提供功能的一小部分。诸如Bigtable5和Dynamo6之类的白皮书彻底改变了行业，并推动了可扩展存储层的发展，从而催生了大量受其启发的开源解决方案，如HBase和Cassandra。

由于第一代这些数据存储不支持SQL，它们被称为NoSQL。如今，这个称谓已具有误导性，因为NoSQL存储已经发展到支持诸如SQL方言等特性，而这些特性过去仅在关系型数据存储中可用。

虽然关系型数据库支持更强的一致性模型，如严格的序列化，但NoSQL存储则采用宽松的一致性模型，如最终一致性和因果一致性，以支持高可用性。

此外，NoSQL存储通常不提供连接操作，并且依赖于数据（通常表示为键值对或文档，例如JSON）是非规范化的。纯粹的键值存储将一个不透明的字节序列（键）映射到另一个不透明的字节序列（值）。文档存储将一个键映射到一个（可能是分层的）文档，而没有严格强制执行模式。它与键值存储的主要区别在于，文档会被解析和索引，因此可以根据其内部结构进行查询。

最后，由于NoSQL存储原生支持分区以实现可扩展性，它们对事务的支持有限。例如，Azure Cosmos DB目前仅支持作用域为单个分区的事务。另一方面，由于数据是以非规范化形式存储的，首先就减少了对事务或连接的需求。

尽管NoSQL存储使用的数据模型通常不是关系型的，我们仍然可以用它们来建模关系型数据。但如果我们拿一个NoSQL存储并试图将其用作关系型数据库，最终可能会得到两者的缺点。如果使用得当，NoSQL可以处理传统关系型数据库能够处理的许多用例7，同时从第一天起就具备本质上的可扩展性。8

高效使用NoSQL数据存储的主要要求是预先了解访问模式并相应地建模数据；让我们看看为什么这一点如此重要。以Amazon DynamoDB9为例；它的主要抽象是一个包含项目的表。每个项目可以有不同的属性，但它必须有一个唯一标识项目的主键。

主键可以由单个属性（分区键）或两个属性（分区键和排序键）组成。正如你可能猜到的，分区键决定了数据如何在节点之间进行分区和分布，而排序键则定义了数据在分区内的排序方式，这支持高效的范围查询。

DynamoDB为每个分区创建三个副本，并使用状态机复制来保持它们同步10。写入操作被路由到领导者节点，当三个副本中有两个接收到写入时，会向客户端发送确认。读取操作可以是最终一致性（选择任何副本）或强一致性（查询领导者节点）。足够令人困惑的是，DynamoDB的架构与我们在11.3章讨论的Dynamo论文中提出的架构大不相同。

在宏观层面上，DynamoDB的API支持：

  • 对单个项目的CRUD操作，
  • 查询具有相同分区键的多个项目（可选择指定排序键的条件），
  • 以及扫描整个表。

我们有意设计不实现连接操作，因为它们不具备良好的扩展性。但这并不意味着我们应该在应用程序中实现连接。相反，正如我们稍后将看到的，我们应该对数据进行建模，从而首先就不需要连接。

分区键和排序键属性用于建模表的访问模式。例如，假设最常见的访问模式是按日期排序检索特定客户的订单列表。在这种情况下，将客户ID作为分区键，订单创建日期作为排序键是有意义的：

分区键 排序键 属性 属性
jonsnow 2021-07-13 OrderID: 1452 Status: Shipped
aryastark 2021-07-20 OrderID: 5252 Status: Placed
branstark 2021-07-22 OrderID: 5260 Status: Placed

现在假设我们还希望在订单列表中包含客户的完整姓名。在关系型数据库中，一个表只包含特定类型的实体（例如，客户），而在NoSQL中，一个表可以包含多种类型的实体。因此，我们可以在同一个表中存储客户和订单：

分区键 排序键 属性 属性
jonsnow 2021-07-13 OrderID: 1452 Status: Shipped
jonsnow jonsnow FullName: Jon Snow Address: …
aryastark 2021-07-20 OrderID: 5252 Status: Placed
aryastark aryastark FullName: Arya Stark Address: …

由于一个客户及其订单具有相同的分区键，我们现在可以发起一个查询来检索所需客户的所有实体。

看到我们刚才做了什么吗？我们根据访问模式构建了表，使得查询不需要任何连接。现在想一想，在关系型数据库中，你会如何以规范化形式建模相同的数据。你可能会有一个订单表和一个客户表。并且，为了执行相同的查询，在查询时需要执行连接操作，这会更慢且更难扩展。

前面的例子非常简单，DynamoDB支持二级索引来建模更复杂的访问模式——本地二级索引允许在同一表中使用替代排序键，而全局二级索引允许使用不同的分区键和排序键，但需要注意的是索引更新是异步且最终一致的。

一个常见的误解是，NoSQL数据存储比关系型数据库更灵活，因为它们可以在不预先建模数据的情况下无缝扩展。事实远非如此——NoSQL需要更多地关注数据是如何建模的。因为NoSQL存储与访问模式紧密耦合，所以它们比关系型数据库的灵活性要低得多。

如果本章有一个概念你应该记住，那就是：使用NoSQL数据存储需要预先识别访问模式，以便相应地建模数据。如果你想学习如何做到这一点，我推荐阅读“The DynamoDB Book”11，即使你计划使用不同的NoSQL存储。

随着可扩展数据存储的不断发展，最新的趋势是将NoSQL的可扩展性与关系型数据库的ACID保证结合起来。这些新的数据存储也被称为NewSQL12。虽然NoSQL数据存储在面临网络分区时优先考虑可用性而非一致性，但NewSQL存储则更倾向于一致性。NewSQL存储背后的论点是，对于许多应用程序来说，通过正确的设计，强制执行强一致性导致的可用性降低几乎难以察觉13。这一点，再加上完美的100%可用性无论如何都是不可能的（可用性以9的个数定义），促使人们努力构建具备扩展性的存储系统，但在存在网络分区的情况下，更注重一致性而非可用性。CockroachDB14和Spanner15就是NewSQL数据存储的著名例子。
